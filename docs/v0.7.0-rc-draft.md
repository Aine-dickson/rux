# v0.7.0 release candidate: the author's draft

**Status: draft, for local use while v0.7.0 is being driven.** It describes the
tip of `build/v0.7`, not a released version. It is deliberately not wired into
`site/sync-docs.sh`, so it publishes nowhere and cannot drift the site.

**What it is for.** v0.7 changes more of what an author writes than any release
since v0.3, and most of it is spread across the register in
[As Built](./05-as-built.md), the roadmap entries that built it, and the trap
list in [Author notes](./09-author-notes.md). This pulls the author-facing half
into one place so an app can be written against the candidate without reading
three documents in parallel.

**Where it is not authoritative.** [As Built](./05-as-built.md) wins on every
point of fact; it is generated into `/reference/` and it describes the tip.
Where this draft and that document disagree, that one is right and this one has
a bug worth reporting.

## Running the candidate

The candidate is the tip of `build/v0.7`, at `0.7.0-dev`. Nothing about it is
installed by default, and that is on purpose: a released `rux` from crates.io
sits at 0.6.1, and overwriting it would make it hard to tell which binary
answered a question.

Build it in place:

```
cargo build --release -p ruxlang --bin rux
```

That leaves `target/release/rux.exe`. Run a document with it directly, rather
than putting it on the PATH:

```
./target/release/rux path/to/app.rux
```

**The editor extension has a setting for exactly this.** Point `rux.path` at
the built binary and the extension's formatting, diagnostics and completions all
come from the candidate rather than from whatever `rux` is on the PATH:

```jsonc
// .vscode/settings.json in the app workspace
{
  "rux.path": "C:/Users/USER/Mobile/UI research/target/release/rux.exe"
}
```

To check it took, run **`Rux: Show Vocabulary Source`** from the command
palette. It should name `0.7.0-dev`. If it says the vocabulary is the one
bundled with the extension, the binary is not being found, and every completion
after that is the v0.7 list only because the bundled copy happens to be current
too.

The extension itself is `editors/vscode/ruxlang-0.4.0.vsix`. Uninstall the
Marketplace copy before installing it, since VS Code prefers the higher version
and the Marketplace is at 0.3.0 only until this one ships:

```
code --uninstall-extension Ruxlang.ruxlang
code --install-extension "editors/vscode/ruxlang-0.4.0.vsix"
```

## What v0.7 changes for an author

### Script is no longer stock rhai

This is the change with the widest reach and the least visible surface. The
vendored fork is described in full in [Script](./07-script.md); what matters
when writing an app:

**A function sees the scope it was written in, and can write it.** This retires
the single biggest trap the language had. Every example written before v0.7 puts
state changes inline for this reason, and none of them had to:

```rux
<script>
  let count = signal(0);

  // Works in v0.7. Before v0.7 this silently did nothing.
  fn bump() { count += 1 }
</script>

<template>
  <button @tap="bump()"><text>Add</text></button>
</template>
```

**A missing map property is an error, not `()`.** Strict bindings turn the
quietest failure in the language into a noisy one. The escape hatch ships with
it, and is needed more often than it sounds: data still loading and genuinely
optional fields both want "absent is fine".

```rux
let name = user?.name ?? "anonymous";
```

**Truthiness is JavaScript's, not rhai's**, `++` exists, arrow functions are a
call form, and a float indexes an array. The full list of divergences, with the
reason for each, is in [Script](./07-script.md). Reading rhai's own
documentation without that list is now actively misleading.

### `position` honors all five values

`static`, `relative`, `sticky`, `absolute` and `fixed` all mean what CSS says.
`static` is the default and is the only one of the five that is **not** a
containing block.

This is worth reading twice if any pre-v0.7 file is being ported, because it is
not a feature that was added so much as four wrong answers that were removed.
Until v0.7 the parser read `"absolute" | "fixed" => Absolute, _ => Relative`, so:

- `fixed` was silently `absolute`, and scrolled away with its ancestor
- `sticky` and `static` were both silently `relative`, so `static` even honored
  insets
- **a misspelled value was `relative` too**, so a typo and a rule that does
  nothing looked identical

And a fifth, larger one: `absolute` was measured against the **parent**, where
CSS measures against the nearest ancestor that is not `static`. It was invisible
because the default used to be `relative`, which made every box a containing
block, so the two rules agreed for a direct child and disagreed only when an
unpositioned wrapper sat in between. Every example in the tree already wrote
`position: relative` on the box it meant, out of CSS habit, and was being
ignored while getting the right answer anyway.

The practical consequence for new code: **the box you are measuring against has
to say so.**

```css
.panel  { position: relative; }        /* say it, or the cover finds an ancestor */
.cover  { position: absolute; top: 0; right: 0; bottom: 0; left: 0; }
```

(`inset` as a shorthand property is not honored, so the four sides are written
out. It *is* a name `transition` accepts, where it stands for all four moving
together.)

A `fixed` or `sticky` box with no inset named now warns rather than doing
something arbitrary, since neither has a legal-but-useless answer worth giving
in silence.

### A `transform` makes a containing block

Whatever the box's own `position` says, and for `fixed` descendants as well as
`absolute` ones. This is CSS's rule and it is the reason `position: fixed` stops
being fixed inside a transformed parent.

It is not an oddity to work around. A transform moves the whole subtree, so
there is no way to hold a descendant still against the window while its ancestor
slides. CSS gives `filter`, `perspective`, `will-change` and `contain` the same
power; none of those is honored in Rux, so `transform` is the only one that can.

Where this bites: an animated page wrapper with a `transform` on it, and a
`position: fixed` toolbar inside it. The toolbar rides the animation.

### `sticky`

In flow, and **its insets are thresholds rather than offsets**. The box sits
where it was laid out until its scroller's edge reaches the threshold, then
rides that edge, and stops again when its own parent runs out from under it.

```css
.section-heading {
  position: sticky;
  top: 0;
}
```

Two things about it are worth knowing before writing a list of sections:

**Inside a scroller the parent it clamps to is the scroller's content box**, not
the part of it currently on screen, which is itself sliding. This is the half
that makes a list of sections work and would have been easy to leave out.

**Two sticky boxes never interact.** A list of sections looks as though an
arriving heading shoves the one at the top out of the way. Neither can see the
other; each is clamped to its own section, and one section's bottom edge is
where the next section's heading begins. The hand-over is emergent. Written as
flat siblings of the rows instead of inside their sections, every heading shares
the scroller as its parent, they all pin at the same edge, and they stack. That
is right, and it is the opposite of what it looks like.

### `<path>`: vector geometry as an element

The full SVG path grammar (`M L H V C S Q T A Z`, absolute or relative), in the
element's own coordinates.

```rux
<template>
  <path class="mark" d="M 12 2 L 22 20 L 2 20 Z" alt="a warning triangle" />
</template>

<style>
  .mark {
    fill: #f9e2af;
    stroke: #1e1e2e;
    stroke-width: 2;
    stroke-linejoin: round;
  }
</style>
```

**Paint is CSS, not attributes.** `fill`, `stroke`, `stroke-width`,
`stroke-linecap`, `stroke-linejoin` and `fill-rule` are honored properties,
which is what gives a path `:hover`, `:class` and `transition` on the day it
lands.

**`:d` binds an expression**, so a chart is a computed path. Two paths with the
same command sequence interpolate under `transition: d`.

```rux
<path :d="spark_line(readings)" class="spark" />
```

Three things it does not do, each deliberate:

- **`width` does not scale the drawing.** Geometry is in the element's own
  coordinates; a width changes the box the drawing sits in. Scaling is
  `transform`, which every other element already uses for the same thing. A
  `viewBox` was considered and not built.
- **A fixed-coordinate path runs off a narrow window.** It follows from the
  above and it bit the first chart written against it. Choose coordinates for
  the smallest box the drawing will sit in, or compute them with `:d`.
- **Two shapes morph only when their command sequences match**, and only when
  both start at the same point and run the same way round. Resampling is not
  attempted, because guessing a correspondence folds as often as it morphs. A
  morph that turns the shape inside out is almost always the start point.

A `<path>` with no `alt` is treated as decoration and left out of the
accessibility tree, which is deliberate: announcing an unnamed graphic is worse
than skipping it.

### Route guards

`guard="expr"` on a `<router>` (every navigation it handles) or on a `<route>`
(whenever that route is part of the match). Outermost first.

vue-router's answers, and they are worth memorising because the third one is the
useful one:

- `false` cancels the navigation
- a string redirects to that path
- **anything else allows it**, and anything else includes `()`

That last rule is what makes the natural shape work: a function that falls off
the end has consented.

```rux
<template>
  <router guard="ready">
    <route path="/" view="home" />
    <route path="/account" view="account" guard="gate()" />
    <route view="not-found" fallback />
  </router>
</template>

<script>
  let signed_in = signal(false);
  let ready = signal(true);

  fn gate() {
    if !signed_in { return "/login"; }
    // falls off the end, so it allows
  }
</script>
```

**They run before the history moves.** A refusal therefore leaves no entry
behind and opens no route transition. This is what makes them worth having on
the route rather than inside the page: by the time a page could refuse to render
itself, both have already happened.

It follows, and this is the half that is easy to leave out because every test
written by hand navigates forwards, that **`back`, `forward`, `replace`,
`go_to` and a deep link all pass through them too.** A guard covering
`navigate` alone protects nothing.

A circle of redirects is cut off at 8, the same bound an `emit` chain has.
Guards are compiled at load, like handlers, so a broken one is reported without
anyone navigating.

### Reading elements from script

`query("selector")` finds an element by CSS selector, **in a handler**, against
the frame already laid out.

```rux
<script>
  fn scroll_to_latest() {
    // `query` answers with a list, so index it. An empty list is the answer
    // when nothing matched, rather than an error.
    let found = query("#last");
    if found.length > 0 { found[0].scrollIntoView(); }
  }
</script>
```

Two constraints, both load-bearing:

**Reads only, and only from a handler.** There is no frame to measure before one
has been laid out, and mutation was cut deliberately: the document and the shell
own different halves of the state, and a script action that touches interaction
state (focus, scroll, selection) is a *request* the shell honors on its next
frame, not a write. The alternative, letting script write the tree directly, is
how `focus()` came to paint a caret and swallow every key.

**A selector string is a string.** `'x'` is a character in this script language,
not a one-character string, which is a real way to write a selector that never
matches.

### Animation: `transition` and `r-transition`

`transition: <property> <duration> <easing>` on any element, for the properties
that can meaningfully be interpolated. The editor's completion list is the
runtime's own list, so it is the cheapest place to check one.

`r-transition` on an `r-if` branch or a keyed `r-for` row holds the element on
screen while it leaves. Style the two ends with `:enter-from` and `:leave-to`,
and the element's own `transition` sets how long.

```rux
<view class="panel" r-if="open" r-transition>…</view>
```

```css
.panel            { transition: opacity 200ms ease-out; }
.panel:enter-from { opacity: 0; }
.panel:leave-to   { opacity: 0; }
```

`:r-transition="expr"` hands the progress to you instead, 0 to 1.

Two consequences worth having in mind before the first one misbehaves:

**A departing element keeps its place until the swap commits.** That is usually
wanted (a dropped list row should not make the list jump) and sometimes not (a
page swap wants the space handed over at once). `position: absolute` on
`:leave-to` is how to hand it over early, and it works because a box with no
inset keeps its static position rather than being moved.

**The duration is read off the computed style.** So a rule at a higher
specificity that changes `transition` changes how long a swap lasts, not just
how long a walk does. That is the intent, and it still surprises.

Two `r-if` / `r-else` branches authored to cross over will **queue instead**,
one below the other, because both are genuinely on screen during the swap. A
crossover needs a shared positioned box with the leaver pinned to its origin.
`<router>` escapes this only because it builds the outgoing page first.

### Lifecycle: `mounted` and `unmounted`

Inline bodies at the top level of `<script>`:

```rux
<script>
  mounted {
    print("on screen");
  }

  unmounted {
    print("gone");
  }
</script>
```

Document level. A component that declares one is warned rather than silently
ignored.

### Gestures beyond `@tap`

The gesture vocabulary landed in v0.7: `@press`, `@release`, `@longpress`,
`@swipe` and `@drag`, alongside `@tap`.

- `@press` / `@release`: `event.x` / `event.y` are relative to the element,
  `event.pageX` / `event.pageY` to the window, and `event.touches` lists every
  finger down
- `@longpress`: once, after half a second held still
- `@swipe`: once, at the end of a press that travelled far enough fast enough.
  `event.direction` is `left`, `right`, `up` or `down`
- `@drag`: at the start, on every move, and at the end. `event.phase` says
  which; `event.totalX` / `event.totalY` measure from where the press landed,
  `event.moveX` / `event.moveY` from the previous event

**A `@drag` claims the finger**, so the page under it does not scroll. And an
element with only `@drag` is deliberately **not** a tap target, so it does not
swallow a tap meant for whatever is beneath it. `@tap` is the finished gesture
and is what a keyboard activation produces.

Every event already reports a *list* of touch points rather than one synthesised
pointer, but no desktop here can produce two fingers, so multi-touch is untested
against hardware and nothing yet interprets a pinch or a rotate. That is v0.8's.

### Component styling changed, and `<style scoped>` is the opt-out

Document rules now style the components the document uses. This was chosen
deliberately in v0.7 and it is a change in behaviour: a component and its caller
that share a class name now collide.

`<style scoped>` opts out, and means the same thing from either side.

Related and worth knowing separately: **variables cascade into components, rules
do not.** A `--brand` set on the document reaches a component; a `.card` rule
does not, unless the document's sheet is unscoped as above.

## Things that will look like bugs and are not

The full register, with the destination each one has to be documented at, is
[Author notes](./09-author-notes.md). Every entry there is a v1.0 blocker.
Distilled, for someone writing an app this week:

| What you write | What happens, and why it is right |
|---|---|
| A cover that fills the wrapper instead of the panel | `absolute` measures against the nearest **non-static** ancestor, and `static` is the default. The box you mean has to say `position: relative`. |
| Sticky headings that pile up rather than hand over | Two sticky boxes never interact. Written as flat siblings they share one parent and all pin at the same edge. Put each heading inside its own section. |
| `width` on a `<path>`, expecting it to scale | Geometry is in the element's own coordinates. Scale with `transform`. |
| Two shapes that refuse to morph | Command sequences must match, and both must start at the same point and run the same way round. |
| A closure inside `filter` / `map` that cannot see the surrounding scope | A method call passes its receiver by reference and the scope cannot also be borrowed, so method dispatch does not capture. A plain call does. Use a loop, or lift what the closure needs into a parameter. |
| `cond ? a : b` | There is no ternary. Use `:class='#{ name: expr }'` or `r-if`. |
| A `@tap` box that only exists to swallow a tap, taking a focus ring and a Tab stop | A `@tap` box is an interactive element by definition, and there is no way yet to say "tappable but not focusable". A scrim that dismisses needs the dialog above it to be a tap target of its own, or the tap falls through. |
| A document that grows past the window and simply clips | Nothing scrolls unless told to. `overflow-y: auto`. |
| A `<path>` a screen reader says nothing about | No `alt` means decoration, deliberately. |

## What is not in v0.7

Naming these up front is cheaper than discovering them mid-build:

- **`rux build`.** Moved to v0.8, where it is the first item. There is no bundle
  and no standalone executable; a `.rux` app runs through the `rux` binary.
- **`rux.toml`.** Lands with packaging, for the same reason: a window title, an
  icon and a target have nowhere to live until there is an artifact to put them
  in.
- **Real unmount for components.** `unmounted` is document level. Instance
  pruning is what a component-level hook is waiting on.
- **Multi-touch, pinch and rotate.** The vocabulary is there and the second
  finger is not.
- **Native pickers** for `<input type="select">`.
- **True inline text flow.** Two `<text>` siblings still stack. This is the
  standing known ceiling, not a v0.7 gap.
- **`/learn` is no longer a gap.** It was three releases behind and still said a
  rhai `fn` cannot read or write a signal, which v0.7 makes false. It was
  brought up to the candidate on 2026-08-19, so its chapter on state now teaches
  the working form. It goes live with the release, not before: the standing rule
  is that it documents the latest *release*, and until v0.7 ships, the published
  copy is still the one v0.6 readers need.

## What to write down while driving it

Two registers, and the difference between them decides which one an observation
goes in:

**[`docs/08-user-tests.md`](./08-user-tests.md)**: what a person actually drove,
per feature, on what hardware, and what the run found. Almost every expensive
bug in Rux was found this way rather than by CI, which is the argument for
filling it in while the app is being built rather than at release time.

**[`docs/09-author-notes.md`](./09-author-notes.md)**: "the engine is right and
the author was wrong" is a finding, not a non-event. One row per trap: what was
written, what actually happens, why that is right, and **where the explanation
has to land**. A trap with no destination is not finished being thought about.

For the extension specifically, the thing worth noticing is any moment the
editor was silent when it could have spoken: a completion list that did not
open, a value accepted that the runtime later warned about, a name that resolved
to nothing on `F12`. The vocabulary pipeline exists so that the editor cannot
offer what the runtime does not honor, and a gap in the other direction (the
runtime honors it, the editor never mentions it) is the failure mode that
pipeline does not catch by itself.
