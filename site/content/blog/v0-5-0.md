v0.4 put Rux in front of other people, mostly through the playground. This
release is about what those people ran into immediately: no way to check a file
without opening a window, no way to format one, warnings that said what was
wrong without saying where, and a text input on a phone that quietly refused to
raise a keyboard.

## What landed

**`rux check`.** A file can now report its own problems without a GPU, a window,
or a person watching. Output is the shape every compiler uses,
`path:line:col: severity: message`, with `--format json` for an editor and
`--deny-warnings` for a CI job that wants a clean file or none. Exit codes
separate the three outcomes that matter: clean, the file has problems, the tool
itself failed. The part worth stating is that it loads through the same path the
window does, so it cannot drift into checking a dialect nothing runs. One
deliberate asymmetry: walking a directory skips components, because a component's
props come from the parent that passes them, and checking one alone reports every
prop as an undefined variable. A checker whose default output is four false
failures is one nobody keeps in CI.

**`rux fmt`.** In place, or `--check` for CI, or `--indent <n|tab>`, or `-` to
read stdin and write stdout, which is what an editor wants. It indents markup by
tag and bracket depth and pretty-prints CSS, inlining rules of up to three
declarations and expanding the rest.

The interesting consequence is a deletion. The VS Code extension carried its own
JavaScript re-indenter, a second implementation of the same rules that could
disagree with the real one and had no tests. It is gone. The extension now shells
out to `rux fmt` for formatting and `rux check` for diagnostics, which means it
needs no TypeScript build, and means there is one definition of what formatted
Rux looks like instead of two drifting ones.

**Warnings that carry a line.** A warning used to be a bare string. It is now a
`Warning { message, line }`, and CSS warnings carry the line in the file's own
numbering rather than the `<style>` block's. Two categories stay deliberately
unplaced: expression failures, and CSS that arrived from a component. A warning
has no file field, so a line drawn from another file's numbering would point
confidently at the wrong place, and confidently wrong is worse than absent.

The dev overlay can also be dismissed now, by tapping it. The dismissal is
remembered against the diagnostics it was for, not as a flag, so hiding "3
warnings" and then introducing a parse error brings the panel straight back. A
boolean would have left the window silent about the new problem until restart.

**Diagnostics in the playground.** `diagnose(source)` returns the error, with
line and column, and the warnings, with lines, as JSON. The page lists them, and
each one is a button that selects that line in the editor. The playground had
been running the v0.3 runtime, reporting no positions and no warnings at all,
which made it the worst place to meet Rux for the first time and also the most
likely.

**An IME, and a soft keyboard on phones.** The report was simple: on a phone, on
the playground, tapping a text input did nothing. Two separate causes.

The desktop shell had no IME at all. It never called `set_ime_allowed` and never
read `WindowEvent::Ime`, so there was no composition anywhere, and dead keys,
accents and CJK had never worked on the desktop either. It now requests
composition on focus, carries the provisional range so the painter can underline
it, and restores the field when a composition is abandoned rather than committed.

The web half is stranger. A browser raises a phone's keyboard only for a focused
DOM element, and Rux paints into a `<canvas>`, which is not one. So the shell
keeps a real hidden `<input>` positioned over the focused field, with
`pointer-events: none` so taps still reach the canvas, focused only in response
to a tap. It holds the real text, which hands composition, autocorrect, dictation
and backspace to the browser rather than reimplementing four hard things badly.
It is enabled on touch devices only, because taking DOM focus off the canvas is
where winit is listening for keys.

The trap in that work is worth writing down: a browser counts carets in UTF-16
code units and Rux indexes bytes, and the two agree only on ASCII. Getting it
wrong does not nudge the caret by one, it panics on the first slice that lands
inside a character. Those conversions are deliberately kept off the wasm
configuration so they can be unit-tested, and writing the tests immediately
caught a rounding inconsistency.

## The bug only looking would find

The headline feature of this release is warnings that carry a line. The line was
wrong.

lightningcss records a source location for a *rule* and none for the declarations
inside it. The cascade set the reported line once, around the whole rule, so
every warning from a rule pointed at the rule's selector. In a stylesheet written
the way people actually write one, that is not a rounding error. A probe file
with three unhonored properties on lines 15, 16 and 21 reported them as 9, 9 and
18: never the right line, twice the same line, and every one of them pointing at
a line where the named property does not appear.

The test suite was green, and the test was not even careless. It checks all three
kinds of CSS warning, and it goes further than most by asserting that each
reported line really does contain the thing complained about. It passed because
every rule in its fixture is written on a single line, `.b { float: left; }`, so
the selector's line and the declaration's line are the same number. The assertion
was right. The fixture could not tell the two apart.

Nothing but opening the window and reading the panel would have caught it, which
is the whole argument for the rule this project keeps relearning. The fix scans
the source forward from the rule for the declaration, stopping at the closing
brace so a missing property borrows no line from the next rule. The test now has
an expanded rule in it.

There is a smaller one in the same family, and it is a warning rather than a bug.
The formatter disagreed with all 28 bundled examples, every one of them, the
first time `--check` was pointed at the directory. Half differed on indent width
and half on inlined CSS. The examples have been reformatted, which is the honest
resolution: a formatter whose own repository fails its check is not a formatter
anyone should adopt.

## What this release is not

**Rux is still not on crates.io.** The v0.4 post said v0.5 would publish, and it
has not. The install story is unchanged: `cargo install --git`, or a prebuilt
binary from the release. The reason is not that it was forgotten but that
publishing is a one-way door. Yanking a version hides it, it does not remove it
or free the name, and nothing can be published over it. The workspace also cannot
publish as it stands: 24 intra-workspace dependencies are bare paths with no
version, up from 13 two releases ago because the count grows every time a crate
is added. That is mechanical work, and it wants doing on a day when it is the
only thing being done.

**The soft keyboard has never met a phone.** It was built from a report, driven
in a desktop window, and exercised through browser touch emulation against the
shipped wasm build. Emulation cannot make a keyboard physically rise. This is
precisely the situation the last release's post described as a reason to distrust
a path rather than to call it done, so it is written here as an open question and
not as a feature.

Warnings from failed expressions, and warnings from a component's CSS, still
carry no line. That is deliberate, but it means the overlay can still tell you
what is wrong without telling you where.

`rux check` finds what the runtime finds, which is not the same as what a type
checker would find. rhai returns `()` for a missing map property, so
`{{ user.nmae }}` still renders empty and silently, and `rux check` will not
mention it.

Unchanged and still the largest gap: there is no true inline text flow, so two
`<text>` elements cannot share a line and bold inside a sentence is not
expressible. A component takes props but cannot emit events or render children.
`r-for` has no keys and reconciles by count. The reactive tier has no effects or
computed values. There is still no mobile code in the repository.

## Next

crates.io, on its own, with the version work that has to come first. After that
v0.6 is about applications bigger than one screen: external CSS, component slots
and events, a router, keyed `r-for`, and computed values.
